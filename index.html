FableOps

A two-player co-op survival game, played on two computers over a LAN. I wrote the networking myself: a host/client setup that sends typed messages back and forth, so both screens show the same enemies, health and puzzle state. In level 1, one player types in code fragments to unlock a reactor while an alert meter fills up and enemies close in.

The hard part

Working out what to send over the network. Sending the whole game state every frame was too much, and sending only player inputs let the two games slowly drift apart. Level 1 ended up with eleven message types, including enemy state, alert meter, wrong answer and player died. Most of them exist because something went out of sync without them.

URL Shortener

Paste a long link and get a short one back, along with a QR code. Each click is counted before the redirect happens. Codes are random six- character strings, checked against the database so the same code never gets handed out twice. Database credentials come from environment variables, so they aren't stored in the repo.

Why not a to-do app

I wanted a project small enough to finish that still had real parts to it: routing, a database and click analytics. It was also the first time I built a backend and a frontend together, and the first thing I deployed.

Hotel Management System

A terminal booking system built for an OOP course. You search rooms by location, date and price, then book one. Most of my work was in billing: I moved payment processing into its own class, pulled shared code into a base class, used templates for the menu handling and added proper error handling. I also overloaded the date operators, so a stay length is just one date minus another.

If I rebuilt it today

I'd use a real database instead of hardcoded data, add an API to simulate actual bookings, and fix the booking flow. We asked for the location and room before the dates, which is the opposite of how booking sites work, and I only noticed once it was built.
