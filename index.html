Ch. 01 — About

The short version

I like the part of a problem where the pieces have to agree with each other. Most of what I build ends up there eventually — two machines holding the same state, one class quietly doing three jobs, an interface that made perfect sense to the people who built it and to nobody else. FableOps

A two-player co-op survival game where both players are on separate machines over a LAN. I wrote the networking from scratch — a host/client session model with its own typed message protocol, because the two screens have to agree on enemy positions, health and puzzle state without ever drifting apart. Level 1 is a reactor room: one player enters code fragments while an alert meter climbs and an enemy swarm closes in.

The hard part

Deciding what to send over the wire. Sending whole world state every frame is simple and doesn't scale; sending nothing but inputs means the two machines quietly disagree. I ended up with eleven separate message types for level 1 alone — enemy state, alert meter, digit accepted, wrong answer, reactor unlock, player died — each one existing because something desynced without it.

URL Shortener

Paste a long link, get a short code back, and it tracks the clicks — plus a QR code endpoint for each link. Codes come from a cryptographically secure generator with a collision check against the database before anything is handed out. Every database credential comes from an environment variable with a safe default, so nothing sensitive is ever committed.

Why not a to-do app

I wanted something small enough to actually finish that still had real parts to it — routing, database design, and analytics. I kept a running log of decisions in the repo while building rather than writing it up afterwards, so the reasoning is still there when I go back to it.

C++ · OOP · Sem 03

Hotel Management System

A terminal booking system for my OOP course — search a room by location, date and price, then book it. I took billing apart: pulled payment processing out of the billing class into its own type, moved shared behaviour up into a base class, templated the menu handling, and replaced silent failures with real error handling. I also overloaded the date operators, so working out a stay length reads like ordinary subtraction.

If I rebuilt it today

A real database instead of a hardcoded one, an API to actually simulate booking, and fixing the flow — we asked for location and room before dates, backwards from how every real booking site works. I didn't notice until it was already built.
